# Flyseri platform

Phase 4 adds a private customer document vault and trip-linked visa application planning. Phase 5 adds guarded flight-shopping infrastructure and customer screens. Phase 6 adds the internal flight-selection and booking-intent foundation. The imported public frontend remains the visual baseline. Public destination examples and Seri chat responses are **demo content**; no booking or live external travel provider is connected until the account's Sabre contract is verified.

## Local setup

Requires Node 24 and Corepack. Run `corepack pnpm install`, copy `.env.example` to `.env`, then run `corepack pnpm dev` to start both the website and API. The site runs on `http://localhost:8443` and the API on `http://localhost:3001` by default. Vite proxies `/api` to the API. `corepack pnpm dev:web` and `corepack pnpm dev:api` start them separately; the visa pages need the API running to load saved profiles and published services.

Run `pnpm build`, `pnpm typecheck`, `pnpm lint`, and `pnpm test` before submitting changes. `GET /api/v1/health` checks API liveness; `GET /api/v1/health/ready` checks configured optional dependencies. Every API response includes `X-Request-ID` and a JSON request ID.

## Infrastructure

`DATABASE_URL` accepts a PostgreSQL connection string, including Supabase PostgreSQL. Drizzle owns the customer, traveller, trip, destination, relationship, and audit tables. Run `pnpm --filter @flyseri/database db:migrate` after setting a development PostgreSQL URL. A configured database can be checked through readiness; without it, the public site and API still start, but customer and trip endpoints are unavailable. For the hosted project, use TLS certificate verification (`sslmode=verify-full` and the project CA file). The project administrator can provision a restricted API login with [supabase/flyseri-api-role.sql](supabase/flyseri-api-role.sql) after creating `flyseri_api` with login enabled and no administrative privileges. The dashboard does not assign a password when creating that role. On the developer computer, run `./scripts/set-flyseri-db-url.ps1` to generate a random password, store the connection URL in the ignored `.env`, and copy the `ALTER ROLE` statement to the clipboard. Paste and run that statement in the project's Supabase SQL Editor, then press Enter in PowerShell to clear the clipboard. Keep migrations on a separate administrator connection; the API login has data access only to the listed application tables.

`REDIS_URL` is optional for local development and required in production. Customer and trip mutation rate limits use atomic Redis counters and fail closed on a production Redis outage. No customer, traveller, or trip records are cached in Redis. Cache keys use `flyseri:dev:`, `flyseri:test:`, or `flyseri:prod:` prefixes.

## Configuration and secrets

`APP_ENV` is `development`, `test`, or `production`; `API_PORT` sets the backend port; `WEB_ORIGIN` sets the allowed CORS origin and is required explicitly in production. `DATABASE_URL` and `REDIS_URL` are backend only. `SUPABASE_URL` and `SUPABASE_ANON_KEY` configure server token verification; matching `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` configure browser authentication. The anon key is public. Never put a service-role key, database URL, Redis URL, or other secret into `VITE_*`. `VITE_API_BASE_URL` may be a public API URL or relative path.

## Customer accounts

Create a Supabase project and enable email/password authentication. Add the site origin and `http://localhost:8443/reset-password` as permitted authentication redirect URLs. Put the project URL and public anon key in both backend and `VITE_` variables, set a PostgreSQL `DATABASE_URL`, then run `pnpm --filter @flyseri/database db:migrate`. Set `REDIS_URL` in production. Deployment must serve customer web routes through the SPA fallback.

The browser uses Supabase only to obtain and restore an access token. Customer profile and traveller data go through the guarded Flyseri API. The API verifies each token with Supabase and derives the internal customer ID from the verified user ID. The first authenticated request creates the internal customer safely. `GET/PATCH /api/v1/me` and `GET/POST/PATCH/DELETE /api/v1/travellers` are the Phase 2 business endpoints; DELETE archives a traveller. Date of birth is stored as a PostgreSQL `DATE` and returned as `YYYY-MM-DD`.

The migration enables PostgreSQL row level security on all customer tables with no browser role policies. Use a dedicated backend database role with table access and owner or bypass-RLS privileges; do not make the browser's anon/authenticated roles owners or grant them bypass-RLS. Keep the PostgreSQL connection string server-side. Live authentication and migrations require your own Supabase project; automated API tests use an in-memory PostgreSQL adapter and a test token verifier.

## Trips and workspace

The `trips` table holds customer ownership, optional title and dates, status, and archive state. Ordered `trip_destinations` and `trip_travellers` connect places and people without putting later visa, flight, booking, or payment fields on the trip. Dates are PostgreSQL `DATE` values. Trip creation checks that every selected traveller belongs to the signed-in customer, then writes the trip, destinations, travellers, and audit event in one transaction. All trip reads and changes scope by the verified customer ID. Trip tables also have row level security enabled without browser role policies.

`GET/POST /api/v1/trips` lists and creates trips. `GET/PATCH/DELETE /api/v1/trips/:tripId` reads, updates, and archives a trip. Nested `/travellers` and `/destinations` routes manage participation and ordered stops. The list supports `status`, `period=upcoming|past`, and `archived=true` filters. The authenticated site offers `/app/trips`, `/app/trips/new`, and `/app/trips/:tripId`. Visa and Documents lead to Phase 4 screens; other future service cards remain inactive and contain no fabricated provider data.

## Private document vault

Set `SUPABASE_STORAGE_SECRET_KEY` on the API server only. It must never be a `VITE_*` variable or shipped to the browser. With a development Supabase project configured, run `pnpm --filter @flyseri/api storage:setup` to create or verify a **private** `travel-documents` bucket. The setup command refuses an existing public bucket. The bucket restricts uploads to PDF, JPEG, and PNG and uses `DOCUMENT_MAX_UPLOAD_MB` (default 10, maximum 25). `DOCUMENT_BUCKET` can rename it. Run `pnpm --filter @flyseri/database db:migrate` with a development PostgreSQL URL before using the API.

The browser sends a multipart file to the authenticated Flyseri API. The API checks its signature, MIME type, extension, and size, strips unsafe filename characters, and chooses an opaque Storage path. It reserves a database version with a unique idempotency key, writes to Storage, then marks the version uploaded. A retry after completion returns the same version. If finalization fails, the API removes the object and marks the reservation failed. Run `pnpm --filter @flyseri/api storage:reconcile` periodically to remove objects from reservations still `PENDING` or `FAILED` after 15 minutes; its output contains only version IDs if a cleanup needs operator attention. File content and Storage paths never enter request logs.

`GET/POST /api/v1/documents`, `GET/PATCH/DELETE /api/v1/documents/:documentId`, `POST /api/v1/documents/:documentId/versions`, and the access URL routes serve the vault. `GET /api/v1/documents/upload-policy` supplies the current upload limit to the UI. The access routes verify ownership, audit views/downloads, and create a short-lived signed URL only on demand. `DOCUMENT_SIGNED_URL_TTL_SECONDS` defaults to 60. URLs are never stored in PostgreSQL; access responses have `Cache-Control: no-store`. An old version remains addressable by its own version ID even after replacement. Deleting a document archives its metadata and files; no file is permanently purged in this phase.

No malware scanner or staff review process is connected. New versions use `security_scan_status=UNAVAILABLE`; the UI never calls them safe or verified. The interface for a future scanner is in `apps/api/src/document/storage.ts`. Visa documents can be attached for planning, but document submission is blocked until the required files have a real `CLEAN` scan result. Production must provide a scanner and review operations before accepting submissions.

## Visa planning

Visa types and requirements are database-driven and are intentionally **not seeded** with country rules. The trip Visa page shows a clear unconfigured state until verified service data is supplied. Only an active visa type matching a trip destination can be used. Creation checks the customer, trip, and each applicant against both the saved traveller relationship and trip participation, then snapshots the currently applicable requirement definitions for each applicant in one transaction. Changes to definitions do not alter existing snapshots.

The API provides `GET /api/v1/trips/:tripId/visa-types`, `POST /api/v1/trips/:tripId/visa-applications`, and list/detail/action/archive routes under `/api/v1/visa-applications`. Requirement links reference an exact uploaded document version. The server checks application, document, version, and traveller ownership before attaching. Required-item progress is derived from the snapshot and links. Status actions use a centralized transition policy; the browser cannot assign arbitrary statuses. Each change writes audit and status history records with IDs and safe event names. No payments, staff decisions, CRM calls, OCR, or external visa rules are implemented.

## Flight shopping foundation

`POST /api/v1/flights/search` accepts a Flyseri-owned, authenticated search request. The API validates routes, dates, passengers, cabin and currency, and checks trip ownership when a trip is supplied. The browser never submits raw Sabre JSON. The customer UI at `/app/flights` supports standalone search and trip date prefill, with local sort and direct-flight filtering. Trip traveller count is shown as context; it is not assumed to be the number of adult passengers. The public manual flight panel links into this screen; the separately labelled idea and sample previews remain demonstrations.

Redis search identity hashes the normalized request, Sabre environment/PCC context and shopping-policy version. A short result cache (default 60 seconds) and expiring owner-checked distributed lock coalesce identical requests. A separate 15-minute search session stores the customer, search criteria, and normalized customer-safe offers without a raw supplier payload. Customer and provider rate limits plus a provider semaphore bound Sabre traffic. Redis outage uses a small local fallback only outside production; production flight search fails closed to avoid uncontrolled supplier calls. BFM requests have an explicit 12-second default timeout and no general retry; the transport retries a 401 at most once after token invalidation. OAuth token cache TTL is derived from `expires_in` minus a configurable safety window.

The CERT-only BFM v5 adapter uses the [current Sabre BFM v5 OpenAPI](https://developer.sabre.com/rest-api/bargain-finder-max/v5) for `/v5/offers/shop`. It joins grouped itinerary, leg, schedule, fare and baggage descriptors into customer-safe Flyseri offers and retains each selected booking class and operating carrier for revalidation. Unsupported NDC content is excluded. A controlled account CERT request returned 50 real itineraries and the requested MYR currency; the mapper handled all 50. REST OAuth v3 uses the supplied guide. Every Sabre call stays server-side, uses a fixed CERT host, rejects redirects, has a timeout, and logs no token or raw supplier payload. The public 2021 Postman BFM collection uses an outdated `/v2` path; no PROD calls were made. The user-supplied credentials were used only for controlled CERT calls and were not saved in the repository. Adult fares are enabled first; child and infant searches stop before a supplier call until age-sensitive passenger details and account-specific mappings are verified.

## Flight selection and booking intents

The customer can select an offer only from an unexpired, owner-checked server search session. The browser sends `searchId`, `offerId`, selected traveller IDs, optional trip ID, and a UUID idempotency key; it cannot supply an authoritative fare or supplier reference. The API checks passenger count and current traveller and trip ownership, then writes the intent, traveller links, and a PII-free audit event in one PostgreSQL transaction. `(customer_id, idempotency_key)` suppresses duplicate creation. The search session contains normalized Flyseri offer data, and Redis still holds only ephemeral search state; PostgreSQL holds the durable intent. A production Redis outage fails closed.

`POST /api/v1/flights/booking-intents` creates a selection. `GET /api/v1/flights/booking-intents?tripId=…` lists trip selections, `GET /api/v1/flights/booking-intents/:id` restores a selection after refresh, `POST /api/v1/flights/booking-intents/:id/validate` checks a live fare, `POST /api/v1/flights/booking-intents/:id/confirm-price` accepts a changed fare while fresh, and `DELETE /api/v1/flights/booking-intents/:id` removes the checkout selection. Every intent read or change is scoped to the authenticated customer. Removing a selection does **not** cancel an airline booking. `/app/flights/booking-intents/:intentId` shows the saved offer, selected legal-name profiles, current fare and expiry, and requires explicit acceptance of a changed price. Trip Flights shows actual saved selections only.

Migration `0009_glamorous_mandarin` adds `flight_booking_intents` and `flight_booking_intent_travellers`, with foreign keys, ownership and idempotency indexes, checks, and RLS. Migration `0010_mushy_doctor_spectrum` adds an explicit passenger type, currently `ADT` on the verified adult-only path. No PNR, ticket, payment, passport, or raw Sabre payload is stored. The [current Sabre Revalidate Itinerary v5 OpenAPI](https://developer.sabre.com/rest-api/revalidate-itinerary/v5) establishes `/v5/shop/flights/revalidate`; one controlled CERT revalidation of a BFM flight returned a matching itinerary, and the TypeScript-generated request separately returned HTTP 200. A short per-intent Redis lock prevents concurrent validation; per-customer and provider rate limits plus a provider semaphore bound CERT requests. The server compares itinerary segments, currency and amounts, stores the validated fare transactionally, and expires it after `FLIGHT_VALIDATION_TTL_SECONDS` (Flyseri freshness policy, not an airline guarantee). Changed fares require customer confirmation; unavailable or changed itineraries never advance to payment readiness. `FLIGHT_BOOKING_EXECUTION_ENABLED` now supports an explicitly configured CERT-only reservation path; it defaults to `false`. See the booking management section below. Runtime flight service requires server-only Sabre CERT configuration and PostgreSQL; Redis is required in production and uses bounded local fallbacks in development. NDC repricing, child and infant classification, booking contact confirmation remain outside this fare-validation path; reservation execution is described separately below.

## PNR booking management

The customer account now includes `/app/bookings` and `/app/bookings/:bookingId`. Checked adult flight selections can create a CERT reservation after legal-name confirmation, contact/billing entry, matching FlightCheck fare, and approved agency configuration. The booking detail links to order creation only after a PNR is recorded. Duplicate requests restore the existing attempt; unknown outcomes require reconciliation.

Reservation creation remains disabled locally until approved agency details are provided. Add the server-only `SABRE_BOOKING_AGENCY` JSON and enable `FLIGHT_BOOKING_EXECUTION_ENABLED` only for CERT. No ticket issuance is enabled. PNR refresh maps a separate current view of airline segments, passenger names and ticket documents. A narrow CERT cancellation flow rechecks an unticketed flight-only reservation without an order and verifies removal before recording cancellation; uncertain supplier mutations require reconciliation. The user selected PNR implementation first and NDC orders next. The supplied NDC overview and full implementation boundaries are retained in [Booking management reference](reference/sabre/BOOKING_MANAGEMENT.md).
